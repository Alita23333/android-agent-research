## 一、核心裁决建议

由 **Codex 主会话负责产品方向、架构判断、复杂问题定位、探索和主线实现；ZCode Workflow 负责明确任务下的独立复现、测试执行、兼容性验证和证据报告**。

最终产品接受与发布由 Codex 主会话综合证据作出，并承担 Android17 目标机验收。ZCode Android15 的结果是独立验证输入，不能直接替代 Android17 产品验收。

本调整替换的是双方研发职责，不替换产品内核。“ZCode Workflow 作为测试协作方”与“ZCode Core 作为产品 Agent 内核”是两件事。产品继续复用 ZCode Core；不恢复 Kotlin AgentEngine，不转向 DSHA fork，不建立第三套架构。

用户在分支会话中要求产出此计划转交主会话。主会话应先核对最新实际状态，再将新的分工和任务书通过现有文件协议正式同步给 ZCode。本分支文档本身不声称对方已接受调整，不冒充已发布任务或已完成实施。

## 二、产品目标与方向校正

目标仍是：手机独立运行任务与执行能力，联网调用可配置模型，能够理解任务、使用命令与工具、加载技能、处理失败、验证结果并交付产物。

现有路线有效：ZCode 提供 Provider / Session / Context / Skill / Tool loop，Android 宿主提供执行与设备能力，APK 管理运行环境，Gateway / journal 管理动作边界。真实模型、文件、搜索、视觉和会话恢复闭环已经成立。

下一阶段应把主要投入转向“完成有用任务”和“扩展无需改内核”的实际证明。手机 UI 自动化仍保留，但不持续扩展为主线。命令、脚本、文件和产物通常更适合作为可组合工作能力；应尽快验证这条主线。

交接、哈希、证据与回归继续用于减少遗漏。它们服务于具体交付，不独立扩张成另一个长期工程。没有相关代码变化或新的未决问题时，不反复运行全套测试。

## 四、调整后的职责

| 工作 | Codex 主会话 | ZCode Workflow |
|---|---|---|
| 方向与优先级 | 决定目标、阶段范围和取舍 | 报告使用/测试问题 |
| 架构与接口 | 分析并作出决策，保持现有权威边界 | 提供指定源码位置、环境事实和复现材料 |
| 主线代码 | 实现复杂修复、运行环境、Skill和工具集成 | 不自行修改生产架构；缺陷修复需求先回报 |
| 测试设计 | 给出可执行步骤/驱动、成功与失败判据 | 可补充用例，但不能降低判据或改生产代码过测 |
| 独立验证 | Android17 产品验收及源码核查 | Android15 独立运行、复现、兼容性回归 |
| 缺陷处理 | 负责影响判断、根因分析和修复 | 保存失败证据、复测指定版本 |
| 版本与发布 | 决定接受、保留恢复版本、安装产品 | 精确报告所测制品，不自行宣布产品已接受 |

ZCode 的任务要有足够确定性，避免把复杂架构判断交给它再由产品侧反复纠错。关键判据尽量由驱动计算；模型负责报告和解释限制，不以阅读日志后的主观印象替代断言。

双方工作区继续隔离，只通过明确交付文件协调。主线实现由 Codex 维护，测试专用 fixture / harness 可由 ZCode 准备；变更正式代码的例外须来自主会话具体任务，不因遇到失败自动获得权限。

## 五、实施顺序与退出条件

### 阶段一：收尾已确认缺陷

Codex 主会话接手 Gateway 入口缺口的完整分析与最小修复，不等待 ZCode 主导架构方案。读取它已提供的源码和证据，区分正常模型、直接carrier、内部call/selftest等入口。

修复必须复用现有 Gateway 与 journal 契约，保持 hard safety 高于 Full Access / yolo、关键动作不能由allow rule绕过、no journal write→no execution、unattended hard-confirm deny、rollback作为新operation、host owns policy ceiling。授权应绑定具体工具、参数及会话，普通工具不能借内部入口绕过。正常模型路线已有批准如何安全复用、直接入口如何取得或缺失批准时拒绝，由主会话源码分析后确定；不在本计划虚构批准凭证、policy matrix或新journal schema。

同时完成最小滚动方向修复。测试专用长列表与probe尽量置于调试/测试构建，避免把可绕过正常执行边界的测试入口带进正式产品。

本阶段退出条件：

- 已识别的执行入口都有明确授权路径；无有效匹配授权、deny、journal失败以及工具/参数/会话不匹配时，实际执行不可达。
- 正常模型调用仍可用，批准不被扩大为其他调用的授权，取消与错误保持原语义。
- Android17 正向/反向滚动经过重观察证明，at_end单独验证；不是只验证手势发出。
- ZCode Android15 对指定修复版本独立回归；版本差异与未测项单独报告。
- 保存新APK/hash/结果和恢复点，之前通过的版本及失败证据不覆盖。

安全缺口属于已确定不变量的实现修复，不借机重做权限、journal或工作流系统。达到退出条件即进入任务能力阶段。

### 阶段二：完成命令、脚本与文件任务闭环

先盘点实际能力：Android本机可执行路径、Bionic载荷、Bash/Node可否作为用户任务工具使用、Python是否实际具备、进程控制/取消/输出限制、工作目录与workspace边界。APK内存在某个运行时，不等于模型已有可调用的命令工具。

优先复用现有 ToolProvider / AndroidToolDispatcher / ExecutionBackend 等适用边界与AndroidToolRequest、Result、Error、ArtifactRef、Cancellation合同，不重写Agent任务循环。普通命令以应用权限执行；root可用不等于任意任务默认采用root。

运行环境按真实任务需要选择：Android本机能够完成的先完成；Python、Git或其他能力的缺项明确检测并报告，不自行下载安装技能依赖。确需运行时包时再按已授权范围集成并固定版本。只有真实依赖缺项证明本机路径不足时，再评估Ubuntu、PTY或其他后端。

首个任务使用受控测试workspace：用户给出一个包含多种文件的目录，Agent自行观察、形成可核对的整理方案、执行已授权脚本/文件操作、处理一个可恢复错误、重新检查结果，交付变更清单和产物。目录内容为测试数据；删除/覆盖继续服从现有授权与备份规则。

本阶段退出条件：

- 自然语言多步任务在手机执行，不依赖PC代跑；命令工具与文件工具均有实际调用证据。
- 命令具备工作目录、明确退出码、超时/输出预算及可取消语义；失败不能冒充任务成功。
- Agent自主验证结果，产物可查看；中断后的不确定副作用不盲目重放。
- ZCode执行同一任务和失败/取消用例，Codex在Android17完成产品接受。

### 阶段三：证明扩展无需改内核

使用 ZCode 已有 Skill / Tool体系，按原目标补足Android适配。避免第二套Session/Skill/Tool registry。SKILL.md内容是工作指导，不能扩大宿主权限；技能激活、工具注册、运行时依赖是不同事项。

用两个独立例子验收：

1. 新增一个SKILL.md目录及脚本，Agent能够发现/启用并完成“整理测试下载目录”任务，不修改Agent内核。实际生产下载目录留到用户明确范围的日常使用验收。
2. 新增一个独立本地工具进程，通过既有Android Local Tool Protocol JSON-RPC2.0注册/调用，返回结构化结果和可查看产物，不修改Agent循环。

检查依赖缺失能准确终止/报告，不反复失败；工具ID冲突与协议主版本不兼容能拒绝；进程退出、超大结果和取消具有结构化结果。技能更新后运行中任务固定旧版本、新任务选新版本；任务记录可关联技能哈希、工具与运行时版本。确实尚缺的产品管理入口按任务补足，不提前扩展为通用插件平台。

本阶段退出条件是两个例子均实际完成任务，并共用现有授权、日志、取消、产物与恢复机制。只有源码接口和演示文档不算完成。

### 阶段四：收敛为日常可用体验

由用户能直接启动任务，清楚看到进行到哪里、需要确认什么、产生了什么文件，能补充指令、取消和恢复。模型设置、能力可用性、无障碍授权缺失和任务失败要有明确提示。

至少完成三个任务：一个文件/脚本任务、一个搜索与资料整理任务、一个跨文件与手机界面的组合任务。优先暴露真实使用问题，再选择下一能力。

如果同一类实际任务持续遇到明确缺项，再选择PTY、Ubuntu ToolchainProvider、Root、Shizuku、ADB、定时触发或子Agent中的必要项。DSHA继续作为选择性复用来源，不作为产品fork目标。GUI、Skills管理或运行环境体验只实现这些任务所需部分。

## 六、验证与接受规则

把“文件完整性通过”“源码/隔离测试通过”“Android15通过”“Android17产品通过”分开记录；任何一层都不能替代下一层。源码/hash检查证明所交字节及差异，不能单独证明源码就是已测APK的完整构建来源。

每次改动先运行与之相关的测试和已知关键回归；边界修复需要有意义的拒绝/no execution验证。未触及的低影响部分不写镜像实现的测试，不无理由重跑全矩阵。发布前选取必要的真实任务烟测，只有新变更、失败或未决风险才扩大范围。

独立测试者必须能报告FAIL/PARTIAL/NOT_TESTED/UNKNOWN。失败时不扩大权限、不改阈值、不修改生产代码让测试通过。副作用不确定时先核对状态，不能自由重试发送、删除、购买或关键系统动作。

ZCode提交测试证据，Codex负责最终接受。没有复测到的机型/API/真实provider能力不泛化。ZCode具备安全配置的真实接口时可以独立测；凭据缺失明确NOT_TESTED，不通过聊天或交接包发送Key。
